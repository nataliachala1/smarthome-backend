# HU16 — Sesiones backend Shelly LAN-first y AP

Fecha: 19/10/2026. Actualización de backend en `16-dev`, coordinada con Liquibase `020_lan_pairing_method` sobre la release `019_device_pairing_sessions` en la rama `16-dev` de base de datos. El flujo prioriza el Shelly que ya está en la Wi-Fi (`LAN`) y mantiene `AP` para equipo nuevo; Android realiza las operaciones RPC locales. Esta entrega no modifica el proyecto móvil ni certifica la POC física.

## Contratos

Todos requieren JWT y autorización backend de `OWNER` activo del hogar en cada llamada. La sesión queda vinculada al usuario creador. `LAN` y `AP` se aceptan para coordinar el flujo; eso no significa que la comunicación móvil-dispositivo esté automatizada o probada. BLE responde `PAIRING_METHOD_NOT_AVAILABLE` hasta una POC nativa aprobada.

En `LAN`, Android descubre el equipo y llama su RPC en la IP local; en `AP`, Android se conecta a `http://192.168.33.1`. El backend cloud no intenta alcanzar esas IP privadas. Los endpoints heredados `discover`, `identify` y `provision` solo sirven cuando backend y Shelly comparten una LAN autorizada; no son el mecanismo de este flujo. El registro genérico `POST /homes/:homeId/devices` tampoco completa pairing.

El incremento cubre la coordinación de sesión LAN/AP y conserva el flujo AP existente. No incorpora todavía el endpoint propuesto `prepare-mqtt`: no hay proveedor administrativo de identidad validado ni contrato móvil acordado para entregar configuración de uso único. La capacidad MQTT se mantiene explícitamente bloqueada, sin emitir credenciales ni usar las de servicio del backend.

## Estados y reintentos

`PENDING → DEVICE_IDENTIFIED → WAITING_FOR_MQTT → CONNECTED → COMPLETED`; cualquier estado activo puede terminar en `EXPIRED`, `CANCELLED` o `FAILED` según reglas SQL. La expiración es de 10 minutos en esta primera versión. No se guarda como estado de backend el resultado local de Wi-Fi que Android no puede acreditar al servidor.

Las caídas locales, Wi-Fi y MQTT deben permitir reintentar dentro de la sesión vigente. Los errores de red/AP, autenticación Shelly o credenciales Wi-Fi son del flujo local de Android y no se fingen como errores medidos por el backend. Errores API estables incluyen `HOME_OWNER_REQUIRED`, `PAIRING_TOKEN_INVALID`, `PAIRING_SESSION_EXPIRED`, `PAIRING_IDEMPOTENCY_KEY_REUSED`, `PAIRING_DEVICE_ALREADY_REGISTERED`, `PAIRING_MODEL_UNSUPPORTED`, `PAIRING_METHOD_NOT_AVAILABLE`, `PAIRING_SESSION_NOT_READY` y `PAIRING_MQTT_NOT_CONFIRMED` en la respuesta de espera. No hay una política de firmware compatible configurada aún; informar una versión no basta para declararla aprobada.

El backend no registra secretos en DTOs o respuestas. El teléfono no debe enviar contraseña Wi-Fi a la API. El token de pairing es secreto de autorización de sesión, no una contraseña MQTT; `X-Pairing-Token` debe redactarse en logs, tracing y errores de la infraestructura que los capture. BLE aún no está habilitado.

## Límite de cierre

`MQTT.SetConfig` de Shelly admite servidor, usuario y contraseña; `MQTT.GetStatus` informa `connected`. La lectura local de ese estado por Android no demuestra al backend qué cliente se autenticó. La finalización exige evidencia observada por el backend o un componente de confianza del broker, vinculada a una credencial individual y a la identidad reservada. El código de esta entrega no recibe aún ese evento ni emite credenciales individuales para EMQX Serverless; `setup-capabilities` lo declara bloqueado. Por tanto las sesiones y el endpoint de cierre ya coordinan, pero el alta no puede llegar a `CONNECTED`/`COMPLETED` hasta que se valide e integre ese proveedor.

Para LAN, la app debe estar en la misma red, descubrir e identificar localmente, crear sesión `LAN`, reportar identidad y reanudar consultas sin enviar RPC desde el backend. Para AP, debe iniciar sesión antes de unirse al AP, crear sesión `AP`, leer identidad/modelo localmente, enviar Wi-Fi directamente al Shelly, tolerar pérdida temporal de Internet y reanudar la sesión. Las contraseñas Wi-Fi/MQTT no deben guardarse en la base SmartHome, SecureStore, analytics o logs. El modelo/firmware beta, autenticación local, transporte bootstrap HTTP y comportamiento de Android requieren prueba física. El dispositivo creado inicia `OFFLINE`; solo telemetría observada actualiza conectividad. Esta entrega no implementa la provisión individual MQTT, un canal seguro de entrega de secreto, observador del broker, outbox de compensación ni prueba física. El cierre continúa bloqueado y no se declara pairing productivo.
